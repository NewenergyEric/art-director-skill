# 美术总监如何让团队持续做对

概念样板确立视觉策略；生产管理把判断落实到成员任务、批量交付、跨类别组合与后续版本。项目案例的某种画风不构成通用风格要求。团队是否减少返工，需要连续真实批次的数据验证。

## 从方向到团队的交接

按[总监工作流](director-workflow.md)建立或接续定位、整体视觉语言、类别/组件家族、代表样板和交付要求，再把它们拆成生产任务。用户已有明确标准和授权时沿用，不重做访谈。候选参考可以用于探索与首件试用，待实际校准和决定后成为其适用范围的生产基线。

每个任务至少关联：task_id、责任人及内部/外包身份、实际资产类别与适用家族、可枚举的 asset_ids、项目版本与 fingerprint、固定/可变内容、交付阶段、必要审查及依赖。一个人可以负责多个任务；按实际资产和交付关系拆分，不强制每个团队都设七个部门。家族内的成员、状态与渠道变体分别列清，不能把一个总览图等同于整个家族交付。

| 工作流 | 需要保持的共同判断 | 除单件外的检查 |
|---|---|---|
| 角色 | 身份部件、轮廓、表情边界、项目造型语言 | 在对白、关卡和 UI 中的实际尺度 |
| 场景 | 空间与材质语汇、主体背景层级 | 棋盘或交互对象能否稳定读清 |
| 棋子 | 颜色与形状身份、状态编码、描边与留白 | 同屏多棋子、小尺寸、状态之间可区分 |
| 道具 | 功能与稀有度表达、材质和交互关系 | 与棋子、按钮或角色组合时不混淆 |
| UI | 真实文字、图标语汇、控件状态与层级 | 长文案、不同语言、禁用/选中/成功状态 |
| 动效 | 继承对象身份、节奏、轮廓、遮挡边界 | 动态中是否遮挡判断；实际引擎时序与性能 |
| 商品与活动图形 | 商品与品牌身份、活动识别、真实信息来源 | 商品、装饰、文案放在一起时的比例和层级 |
| 版式与多渠道 | 内容优先级、家族区域、可重排与固定部分 | 横竖/多尺寸重排、长文案、裁切与实际渠道展示 |
| 外包交接 | 同一适用规则、版本、交付格式与验收方法 | 交付源文件、使用范围、版本与集成条件 |

这些检查按项目阶段选用。外包不是单独的美术类别；同一资产不能只因来自外部就另用一套审美标准。

## 并行制作时保持什么

每批冻结一个不可变项目包，所有成员在开工和交付时都记录相同 project_id、version 与 fingerprint。版本号相同而指纹不同也需要查明。成员只加载任务适用规则和参考，既不各自重写全项目风格，也不把所有角色身份图混入每个任务。

分发任务时同时给出使用的 Skill、工作目录和唯一输出根。成员先读同一方法与项目包，再按自己负责的资产制作；不要各自在母仓库根建立另一套 assets，也不要把制作文件写回冻结规范包。组合负责人按交付清单收件，保留早期副本但排除它们进入正式导入清单。

依赖按实际文件与用途说明，而不只列前置任务编号。例如 UI 成员继承物品首件的缩略图尺度和留白，动作成员继承角色与工具的连接点，组合负责人检查这些输出在同一画面的比例、对比、材质与文字层级。把说明写进已有任务卡和组合记录，避免另建第二套美术规范。

依赖准备可以并行，依赖未完成的设计保持候选。角色成员可以探索姿态，动效成员可以设计节奏；绑定实际形体后仍要播放复核。共享首件或规则改变时只列出受影响的下游任务，不能因任务表打勾就推定它们自动兼容。资产责任人与最终组合责任人都要明确，Agent 产物使用相同验收要求。

按约定批次收件，保留原始交付文件及其哈希。交付记录用 asset_id 与 task_id 连接原任务；没有文件的计划项保持 missing。收到一个参考总览板不能把清单中的几十项独立资产都标为完成。

## 三层验收都留下证据

1. **版本与交付核对。** 用 [批次协议](team-batch-contract.md) 和 `team_batch.py` 检查项目包、批次/单件基线、任务归属、清单完整性、真实文件哈希、必要评审项及证据文件。它能发现错版、漏件和缺证据，不能判定画面好坏。生产批次的项目批准状态还需真实证据；不能靠把 mode 改成 production 获得批准。
2. **视觉规则审查。** 依据同一版本的实际参考逐项查看 identity、style、task 等适用项。指出部位与规则；unknown 不作通过。例如动效给原本没有五官的棋子添加表情，属于身份变化，不能因“效果更可爱”自动接受。
3. **使用场景与工程检查。** 将实际候选交付组合到目标关卡、界面或引擎中检查遮挡、可读性、文字、时序、格式与运行条件。静态关键帧不能证明动画正确；透明预览不能证明资源已可进引擎。

批次报告中“ready”只表示已满足工具支持的声明和文件条件。review 的 pass 是实际评审过程应提供的记录，脚本不会认证签署人，也不会重新评画。产物阶段、必要未检查项与正式决定分别说明。

## 精确返工与有范围的版本变更

单件问题只退回受影响资产，记录应保留部分与修正范围。错版交付应先核对原因，不能只改版本字段或重算哈希就宣称按新基线制作；复核素材差异，必要时重做并保存新证据。其他资产仍保持自己的待评/通过/失败状态。

共享规则需要改变时，提出：旧/新规则、改变原因、相关样板、受影响类别与资产、依赖、旧资产处理和迁移决定。工作副本保持 draft，原已批准版本不被覆盖。已有明确授权直接执行相应范围，不无故增加逐件总监审批。

选择性迁移采用**新批次固定新版本**：需要新规则的任务进入新批次，其余任务保留旧基线。集成时对依赖做兼容性复核；不能把两个版本的交付直接塞进同一个只声明一个 baseline 的批次，也不能默认版本号更大就适用于所有旧任务。`team_batch.py` 不计算跨批依赖图或替团队决定迁移。

## 持续观察是否改善

按真实批次和类别报告首次通过、身份错误、漏件/错版数量、返工轮次及评审时间；保留分母、未检查项和异常。把问题归因到来源输入、规则歧义、执行偏差或工程约束，再决定调整哪一层。一次概念图成功、脚本测试通过或模拟动画都不能证明团队品质已经稳定。

新构建的 `team-v1` 项目包自带 `style_pack.py`、`project_runtime.py`、`team_batch.py`，可在独立目录调用规则、建立任务与检查批次；`pilot.py` 是母 skill 的附加试点工具。旧包保持其原有内容，需重新构建才能获得新工具。成员的文件和工作记录放在规范包外。
