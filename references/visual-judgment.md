# 把判断做成图例、家族设计与返修证据

用于主美解释难以用一句话传达的取舍、成员扩展一组相关资产，或反馈反复出现时。按当前问题选用下列记录；已有任务书能够承载就补在原处，不要求每张图填三套表。Agent 先用实际资料写好内容，再把真正未定的取舍交给负责人。

| 当前问题 | 使用的记录 | 完成后应能回答 |
|---|---|---|
| “更简洁”“更有体积”等要求容易被误解 | [图解判断卡](../templates/visual-judgment-card.template.md) | 看哪里、为什么、先改什么、必须保留什么 |
| 多个等级、组件、状态或渠道既要统一又要可辨 | [整链／家族设计表](../templates/family-design.template.md) | 共同继承什么，各成员为什么不同，怎样一起验证 |
| 修改一个问题却破坏了别处，或同样的问题反复出现 | [返修前后对照](../templates/revision-comparison.template.md) | 实际改善了什么，哪些保持项被复查，尚有什么不确定 |

完整示例见[我们自己的制作案例](learning-cases/index.md)。案例的尺寸、材质、画风、成员数量和自查结论仅属于案例，不是通用规范。没有对应证据时保留空缺说明，不能为了演示成功而补画一个“历史失败稿”或代签批准。

## 图解判断卡：让别人看懂判断依据

每张卡聚焦一个可复用的判断，用具体图像区域连接观察与操作：

1. **定范围。** 绑定项目版本、规则／家族、使用情境和触发问题。说明是现有规则的解释、新建议，还是某项例外；当前任务的要求不自动成为全项目规范。
2. **指出位置。** 引用实际文件，并用箭头、区域描述或已有局部图指出证据。局部图旁保留完整图入口；只说明某处处理有效，不能批准整张图。没有图时标为文字草案，不声称图解已经完成。
3. **拆开观察和推断。** “门窗缩小后与边框难分”是观察；“边框占比可能过大”是待验证成因。把“更高级、圆润、简洁”等要求落到轮廓、转折、色面、主次或实际可见的状态。
4. **给调整顺序和保持项。** 先处理影响用途的整体关系，再处理局部；根据项目决定手段。减少碎纹理不等于压平体积，强化识别不等于所有部件都加对比。颜色、明暗、结构各自改变了什么要可解释；不要把某种画法变成所有风格的默认值。
5. **定义复查情境。** 图像、交互、文字、运动分别选适用的检查。剪影适合轮廓诊断，但不能判断颜色、透明材质或状态语义；彩色图、真实文字与动态过程仍需各自检查。

并排比较应说明画布、缩放、背景及裁切。为了分析画法可以对齐主体大小；为了判断实际使用，必须保留交付画布、留白和项目显示方式。两种视图职责不同，不能用局部放大或单独缩放证明实际使用已经合格。标注不要遮住待判断区域，也不要烘焙进正式素材。

## 整链设计：共同语言与成员差异同时成立

“链”也可以是分支、并列系列或状态图。游戏等级记录升级关系；UI 记录状态和转换；角色记录姿态／表情中的身份继承；活动素材记录渠道适配。不要给非等级关系硬排高低，也不预设等级数、画布、占格比例、相机或统一材质。

先写清关系和共同继承，再逐成员填写：用途／身份、主要识别线索、允许变化、最易混淆的对象、依赖与组合检查。升级不能只靠更亮、换色、数小装饰；UI 状态也不能只有无法感知的细微差别。差异是否足够，仍以项目的实际使用证据为准。

样板按风险挑选：例如最简成员、重复结构、容易混淆的一对、复杂组合或关键状态转换。只选与当前项目有关的项目；同一件可覆盖多个风险，已有可靠样板可复用。先做能揭示问题的成员，再决定是否扩量，不固定首件数量或强制多套候选。

从单件到关系检查：在实际尺寸或明确标注的试验条件下，观察成对差异、整组主次，以及与其他家族／真实内容同屏的干扰。组合变复杂时检查主体是否被配件挤小；调整主辅关系时保留必要功能。单件、整组与真实运行的结论分别记录。

## 返修对照：验证修正，同时复查保持项

保留实际修前、修后文件和输入记录，注明这是原始输出、导出副本还是合成预览。区分“要求只改这里”和“实际只有这里改变”：生成式编辑仍可能影响其他区域。没有逐像素检查时，不声称其他区域完全不变。

按“问题 → 成因假设 → 本轮改动 → 实际结果”记录。复查范围由依赖决定：棋子可能是相邻等级和跨链混排，UI 可能是长文案、相邻状态和页面组合，角色可能是身份、接触点和受影响镜头。无需把无关资产全部重测，也不能只看修改局部就宣布整体通过。

如果新稿解决了局部却引入其他问题，保留“部分改善／仍需返修”的结论。错误判断应追加更正与理由，保留原记录；不能删除失败过程后宣称一次成功。继续、回退或换方法依照现有授权和任务预算，记录原因。

## 回到同一份项目源并随包交接

三种记录是证据载体，不是第二套规则库：

| 内容 | 已有项目源位置 |
|---|---|
| 可复用且有范围的判断 | `rules` 的 statement、rationale、allowed_variation、evidence、verification 与真实状态 |
| 家族关系、共同继承和变化机制 | `direction.families`，必要时结合 `profiles`、实体与任务变量；详细设计表作为说明材料引用 |
| 图像、局部认可范围、文字案例 | `references` 的角色、notes、provenance；文字记录用 `context`，不用作图像模型输入 |
| 被实际认可的样板与覆盖范围 | `direction.exemplars`；只有真实决定支持时才更新批准状态 |
| 修正决定、迁移与未验证条件 | `decisions`、`open_questions` 及原任务评审记录 |

初稿与返修记录先保存在任务工作目录，绑定冻结版本；不要写进不可变包。需要让成员复用时，从项目工作副本登记所选记录及它引用的每个本地文件，用相对路径关联，校验、升版并重新构建。仅登记 Markdown 不会自动收集其内嵌图片。母 Skill 自带的教学案例不自动进入每个项目包；只分发本项目真正需要且允许分享的证据。

新构建的包在 `guides/03-delivery-review.md` 内带有三种记录的简版方法和表格，成员不依赖母 Skill 目录。项目艺术判断仍取自该包的 JSON、参考及决定；旧包不会随母 Skill 更新自动变化。
