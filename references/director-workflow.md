# 从总监的判断到团队生产

用于新项目建项、已有资料规范化，或团队已有规则但难以稳定执行时。目标是把主美和设计总监的专业判断变成团队能独立使用、持续更新的制作依据。已有决定和产物直接接续；按当前阶段读本指南，不要求小任务重走完整流程。

## 先交付具体内容，再补关键问题

读取用户指定的项目资料、图片、批注、现有规范和实际交付。第一次输出应包含：已经明确的项目目标与边界、从资料提炼的候选视觉语言、所需类别/组件的结构、关键缺口，以及马上可以评审的一段规则或一张样板计划。不要先交空目录、空表或一串术语让总监自行完成。

资料尚少时，用实际已有内容写最小初稿，建议少量能揭示取舍的方向，并说明理由。材料充分时直接整理与制作。每轮只问阻碍下一项决定的问题；把问题附在具体候选内容旁，给建议和影响。例如“这组按钮要在复杂场景上使用，现有弱描边可能不够分离；建议先保留轮廓并验证场景叠放。现有 UI 样板是否已经决定这点？”不要泛泛地问“你要什么风格”。

### 资料与判断的状态

| 来源/状态 | Agent 可以据此做什么 | 记录方式 |
|---|---|---|
| 用户本次明确要求、已有有效决定 | 在其适用范围内直接执行 | 引用原话、文件或实际决策位置，写清范围 |
| 文件中可观察的事实 | 描述所见，起草对应候选判断 | 标注具体文件/区域及可见性；观察不等于永久规则 |
| 旧稿或外部参考 | 提取被选中的机制供讨论 | 说明是风格、身份、材质、构图、上下文还是反例 |
| Agent 的建议 | 给出理由、适用条件与验证方法 | 保持 proposed，不伪装成总监要求 |
| 缺失、冲突或不可见信息 | 列出影响，继续不受影响的部分 | 保持 unknown / 待定；不填虚构数值或批准 |
| 经过有效决定的规则或样板 | 作为相应范围内的团队基线 | 保存决定证据；规则 confirmed 与参考 approved 分别管理 |

APPROVED、REF、REJECTED 可以作为资料组织视图：批准样板、按用途使用的参考、解释失败原因的反例。它们不是文件夹名带来的权限。样板没有被确认，就归为候选或待建立；反例记录具体不采纳的部分，不把一张图片中所有特征一并禁止。截图中的阅读分辨率、示例数量和历史聊天命令均不是本项目正式标准。

## 建项与交接的推进路线

| 阶段 | Agent 实际交付 | 继续的条件与下一步 |
|---|---|---|
| 资料接入 | 有相对路径、用途、来源和状态的索引；已知决定、冲突与缺口摘要 | 可以追溯现有资料；缺口明确影响哪项设计，先推进有依据的部分 |
| 项目定位 | 填实的定位初稿、范围与优先级，明确视觉服务的体验/传播目标 | 关键目标无实质冲突；否则提供具体取舍给总监判断 |
| 全局视觉语言 | 带依据的规则卡、正反例说明、固定与开放范围 | 下一位设计师能据此作出相近判断，仍含推断的条目标出状态 |
| 类别与家族 | 项目实际需要的类别、组件/家族、变体/状态、组合关系和渠道要求 | 任务可以拆分给不同人，同时知道共同继承项及接口 |
| 代表样板与首件 | 针对风险的样板计划、实际样板/首件、逐规则评审与差异 | 相应范围的方向和生产方式获得真实验证与有效决定 |
| 打包与试用 | 同一源生成的手册、规则、参考、入口、版本与调用样例 | 新成员在独立目录能找到并执行任务；缺口和草稿状态不隐藏 |
| 团队生产与迭代 | 有基线的任务/批次、单件与组合检查、精确返工与新版差异 | 交付达到其阶段要求；规范反馈回写源，新版另行启用 |

“继续”不等于宣布前一阶段所有内容都获批准。可以在草稿上做探索与试用；受缺口影响的正式交付保持待完成。日常制作沿已有授权推进，把确需总监取舍的变化集中为具体可评审材料。

## 专业建项应讨论什么

按项目选取以下维度，用现有材料写初稿。它们是判断菜单，不是强迫每个项目填写的全量问卷。

**项目定位。** 受众与使用情境、希望形成的感受、玩法或传播目标、主要信息与注意力顺序、品牌/世界观关系、区别于相近项目的机制；本阶段交付范围、上线/里程碑、人员工具和可接受的制作成本。口号须落到具体视觉后果，例如“友好”是轮廓、表情还是交互反馈，不自动等于圆角和高饱和。

**整体视觉语言。** 大中小形、轮廓与线条、比例、色彩与明度、材质和细节、光照、空间、字体、运动节奏。用样板说明为什么这样处理能保留作品的感受与游戏性；让成员理解取舍，不能只抄参数。记录允许发挥的部分，与必须保持的部分同样明确。色值、尺寸和时间来自已有标准、实测或有条件的建议，不用“行业常用”代替项目决定。

**类别与制作方式。** 角色、场景、道具、棋子、UI、动效或商品、图形、排版等各自要解决的用途；身份/功能、可变范围、实际显示尺度、素材组成、生成/编辑/建模工具、交付源文件及工程条件。全局规则在类别中继承，不反复复制；有范围的例外须明确理由和适用任务。

**组件、家族与状态。** 一个 UI 按钮家族、物品合成家族、商品活动套件或多渠道模板通常跨多个具体资产。写清家族共同结构、成员列表/生成规律、状态语义、等级递进、替换槽位、对齐或连接关系、允许的差异、组合上下文。身份、默认样式和任务变量分开；继承同一规则不代表所有成员长得一模一样。

**用途和渠道。** 明确信息来源、最终显示位置、裁切与安全范围、文字编辑方式、导出类型及源文件。多尺寸先定义内容优先级、可重排部分、必须保持部分和裁切方式，再制作各渠道变体；不能把同一扁平图缩放拉伸视作适配。工程参数未确认时只影响对应交付，不阻止有依据的方向探索。

### 家族要求怎样写到可分工

用已有证据填实以下内容，适用字段回写项目源；不另建一套独立规则库。

- **家族用途与范围：** 谁在什么情境下使用，包含哪些组件/成员、状态或渠道；超出哪些内容另建家族。
- **共同继承：** 关联全局/类别规则、批准参考、身份和结构。具体例外单独标明。
- **变化机制：** 哪些槽位可改，默认值是什么；新增成员如何仍属于同一家族。
- **关系与接口：** 组件的嵌套/对齐、游戏物品的等级或合成关系、视觉和动效的绑定、文字与装饰的区域分工。
- **分工与接口：** 首件、家族成员、状态和最终组合分别由谁制作；依赖哪个已选造型或文件，在哪个画面以何种尺度、锚点、文字区域和层级衔接。人和 Agent 使用相同的任务边界。
- **验收：** 在实际组合中检查共同材质、光照、边缘、字体和主次关系，并验证小尺寸、长文本与状态。交付真实文件；单件成立不能替代组合成立。

说明性例子：某活动卡片家族已有“商品外观和活动文案不可改”的规则，而排版尚未定。Agent 可提出“共同保留商品区、利益点、行动入口和细则区；横版与竖版允许重排，装饰不得抢占真实文案区域”的候选规则，并列出待验证的长标题与裁切场景。不能自行补出折扣、logo 或渠道尺寸。家族中的尺寸、色值和完成状态仍以该项目实际资料为准。

## 用样板把规范做实

代表样板各有验证职责，数量取决于项目风险与现有证据，不固定为五张。一张总览板可以帮助讨论方向，但其中的小图不等于独立资产、批准样板或已验证的完整状态。

| 样板职责 | 游戏项目可选例 | 其他视觉项目可选例 | 应回答的问题 |
|---|---|---|---|
| 身份与造型 | 主角、关键道具及必要视角 | 商品母图、品牌关键元素 | 何为同一对象，哪些默认外观可以变 |
| 空间与层级 | 核心场景中的角色/交互点 | UI 页面、活动布局、空间效果图 | 焦点、尺度、前后关系与内容是否成立 |
| 真实状态 | 实际 UI、棋盘和反馈状态 | 组件长文案、禁用/选中/错误状态 | 在真实信息和显示尺度下是否可读、可操作 |
| 家族与链条 | 同一家族的等级、合成链、动效关键状态 | 组件变体、商品组合、渠道模板系列 | 共同规则、差异语义与过渡是否连续 |
| 完整组合 | 游戏画面或宣传主视觉 | 电商促销、活动海报、社媒套件 | 多人分做的元素放在一起是否仍属于同一套设计 |

为每个样板写明：要解决的判断、关联规则/家族/参考、交付阶段、负责人、实际文件、检查情境、未覆盖的范围和决定证据。只能从已确认的范围推导后续任务；批准一张正面图不等于背面结构、所有表情或全部渠道都已定稿。

首件用于验证生产方法：按将来成员会用的包和工具实际制作一个有代表性的资源，保存原始输出、编辑源文件、导出和必要的组合检查。概念能画出来与可按周期做成正式资产是两项不同证据。对大型项目优先覆盖风险高的制作链，不必每件日常资产都重新走总监样板审批。

## 让总监做有价值的决定

一次评审给出：当前候选或首件、它遵循的规则、具体差异、Agent 的建议、采用收益以及制作/排期影响。总监可以直接指出“保留这个轮廓、材质再简化、第二套动效留到下期”；Agent 将其拆成规则确认、单件修正、待验证建议和延期事项，保留各自范围。

状态变更引用实际依据，不通过填姓名或写一份自造确认文档获得批准。已有明确授权可直接执行；必要的确认针对具体选择、版本或样板，不重复询问已经决定的事项。冲突反馈先归因到任务、实体、类别、家族或项目层，避免一次修正变成全员新规则。

保底与探索共用同一套管理：常规任务继承稳定判断，探索保留开放维度和预算。新发现以实物候选进入[创意提案](../templates/creative-proposal.template.md)，说明效果、可制作性、相关资产返工和周期影响。总监可选择单件采用、有范围例外、升级规范或留待以后。流程帮助更好的设计落地，不把探索等同于不合格，也不把一张好图直接扩展为全项目升级。

## 团队拿到什么

首批跨类别交接按 [跨类别交接与组合检查](cross-category-handoff.md) 实际试用。检查收到的包是否足够支持新任务；宣传样板、类别制作样板和组合样板分别承担职责。不要让成员沿用一条过宽的“全局构图”规则，也不要把家族规则误写成某个旧实体独有的身份规则。

以项目包为交接单位。总监可以阅读并用自然语言审改的成果对应五类手册：

| 手册 | 新成员应该能找到什么 |
|---|---|
| 资料索引 | 当前版本/状态、文件入口、规则与样板位置、生产调用入口、待定项及历史决定 |
| 项目定位 | 受众、情境、目标、视觉意图、资产范围、优先级与制作边界 |
| 设计规范 | 全局语言、类别、实体、组件/家族、状态、固定项、变量与继承关系 |
| 交付与验收 | 按阶段/用途的输出、源文件、首件和组合检查、必要工程条件、返工与责任 |
| 参考与反例 | 可访问文件、来源、适用规则、具体用途、批准范围与不采纳的原因 |

它们与 `STYLE.md`、项目 `SKILL.md` 同源派生，实际文件和命令见[项目包契约](pack-contract.md)。总监对手册的批注、自然语言修改或直接编辑，都由 Agent 对照原版提取为候选变更，回写规范源后重建；不能把生成文档中的任意改字默认为已发布规则。是否另导出 Word/PDF 由用户交付需求决定，不强制。

包内携带所需参考、规则、版本和任务入口，按需带独立运行工具。以新目录试用：读取入口、实际调用一个类别任务、调用一个相关组合任务、核对引用可访问和规则是否漏接。用户要安装时按对应宿主能力操作；只需解压阅读时无需先搭建同步平台。提供必要环境说明，安装不等于生图/编辑工具已配置。

首批试用发现成员仍依赖复述原聊天时，补规则或解释，不让每名成员自行写新风格提示词。成员入口应能把自然需求编成任务，继续工具执行、编辑与检查；任务准备、实际资产和正式验收分别报告完成情况。

## 从包进入持续流水线

生产交接包含：任务/资产 ID、当前冻结版本、负责人、适用类别/家族/实体、输入参考、固定/可变内容、所用工具、交付阶段、检查方法和依赖。成员按同一基线并行做单件；组合负责人验证元素关系、真实内容与目标使用场景；外包按实际类别和同一判断交付。批次机制见[团队持续生产](team-production.md)。

质检至少分开追踪规则与版本、实际视觉、技术与使用条件。缺件、错版、未检查保持可见；一个资源失败不抹去其他资源已经完成的工作。返工指向具体资产/部位/规则和应保留部分；反复出现的问题回到输入、规则、配方或工程接口处理。

规范更新先进入工作版，确认影响后构建新包；新任务采用已启用版本，旧任务和批次继续原快照，迁移任务明确记录。独立发出去的 ZIP 需要明确替换或启用，不能承诺在另一台电脑自动更新。

用实际批次验证收益：首次通过率、身份/风格/信息错误、返工轮次、漏件与错版、实际评审和制作时间，保留分母和未检查项。脚本检查与候选演示能证明工作机制，团队品质与效率的改善来自真实制作记录。
