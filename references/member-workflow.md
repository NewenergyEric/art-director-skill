# 成员按项目规则制作与交付

成员拿到项目包，说清本次用途和变化，Agent 接上已经建立的专业规范、样板和制作方式，持续跟进到实际结果与验收。适用于游戏角色、场景、棋子、道具、UI、动效，以及商品、装饰图形、文字与组合版式；日常制作、系列扩展和新的探索方向都从同一项目基线开始。

可直接这样开始：

> 使用这个项目包。请按现有活动组件家族做一组新内容，并把商品、文案和装饰组合成横版与竖版主视觉。保持品牌和商品外观，读取本次活动表；按已定渠道要求交付，装饰与布局可以在允许范围内探索。

Agent 读取包内入口、五份手册中相关部分及对应规则，拆分组件/组合任务，再执行生成、编辑与检查。已有工作区直接接续；新 `team-v1` 包自带运行工具，可由 Agent 初始化包外工作区，不要求成员另找母 skill 源码或重述建项聊天。实际工具安装与调用按现有环境及授权处理。

## 先找到项目，不从提示词重新建立项目

优先使用用户指定的项目工作区和当前任务。已有任务要求“继续”时恢复其版本；明确新任务时读取工作区当前版本。没有接入工作区但已有项目包时，可由 Agent 建立入口；缺少原始资料时先整理可用证据，不能凭空补成已确认标准。

最少读取：共享风格；当前类别和组合内各组件类别；适用家族及样板；具名实体与身份参考；用途/渠道和交付规格；任务预算。角色或商品别名可映射到稳定实体 ID。如果一个项目有两位女主、多个相近 SKU 或用途相似的组件家族，不能随意选择；先用已有任务、文件或对话消除歧义，只在仍无法判断时询问具体信息。

目录、结构化请求、脚本与记录由 Agent 管理。不要把填 JSON、找哈希、学 CLI 作为成员开始做图的前置条件。对外只说明“这次沿用谁、改哪些地方、交付什么、哪些还未定”。

用户已明确标为涉密的素材，只在其授权项目中使用，不进入公开演示、示例、文档或发布包。公开案例使用独立的原创资料，并检查图片、名称、别名、路径与可跳转的文件；只替换展示名称不等于已移除原素材。

## 把一句话拆成可执行的继承关系

首先读取项目共同判断，再选择实际类别、组件/家族、实体、用途与本次变化。家族约束补充类别规范，例如按钮的状态语义、合成物品的等级关系或活动卡片的区域分工。类别已定义家族时，Agent 从需求绑定 `family`；组合中各组件也分别绑定适用家族。不猜选一个近似家族，不把所有家族规则混在一起。

项目中的固定项与身份仍有效；变量按类别、家族、实体依次取得适用默认值和探索范围，具体覆盖遵循包内 `task_controls`。同名变量出现与硬规则冲突时列明冲突，不能以默认值覆盖顺序代替专业判断。

示例请求：“给米拉换一套雨衣，侧身挥手，做活动登录页人物，保留她的长相。”米拉是公开原创示例角色，深蓝短发；实际项目读取自己的角色资料，不继承示例外观。

| 层 | Agent 自动接入的依据 | 本次变化 |
|---|---|---|
| 项目 | 当前共享风格、全局规则、当前版本 | 不因成员措辞不同重新发明画风 |
| 类别、家族与用途 | 角色 profile、实际适用家族/样板、活动登录页交付规格 | 仅在用途变化时换用适用规格 |
| 实体 | 米拉 ID、身份参考、脸与发型等不变量 | 表情和姿态不会自动放开身份 |
| 任务 | 默认服装、姿势和本次授权维度 | 雨衣与侧身挥手取代对应默认值 |

换装任务必须明确“原来的衣服是默认外观，还是不可变身份”。不能把固定服装、固定脸和固定风格塞进同一个锁，再要求模型同时保留旧上衣和生成新上衣。

新项目在 `task_controls` 中把 outfit、pose 等可变项与默认值分开，实体可以补充自身约束和别名。旧包若仍把衣服写入硬身份规则，不悄悄删除旧规则；在新工作版拆分，或依据本次实际授权记录有范围的例外。明确要求换装，不代表允许改脸、发色或项目整体画风。

组合任务同样适用。例如“商品 A 的活动横幅，包装不改，装饰更活泼，价格和文案沿用本次活动表”：同时读取项目/品牌、商品 `product`、图形 `graphic`、文字 `typography` 和版式 `layout`。从同一基线合并规则与参考，保持商品身份和实际文案，探索授权的装饰与布局；合成后检查层级、留白和渠道裁切。每个元素单独合格不等于组合画面合格。

组合里的子资产有自己的状态、等级或姿势时，分别建立家族任务，再绑定真实输出。例如“锁定的二级花园物件卡”包含二级物件、卡片底板和锁定角标；组合的 `state` 不会自动传给所有组件。当前 `components` 绑定类别、家族与实体，子资产变化由各自任务承载。

Agent 在已有的 `work/<task_id>/composition-inputs.md` 记录子任务、负责人、状态/等级、实际文件、版本和已检查范围，并说明目标画面中的尺度、锚点、遮挡或文字区域。首件依赖与最终组合负责人要明确；缺文件保持待制作。不同成员与 Agent 收到的是同一依据下的具体分工，不各写一段风格提示词。由 Agent 维护记录并查看真实组合，不要求设计师手填，也不改写只读任务快照。

## 生产与探索如何选择

普通制作默认沿用已经认可的方向，避免每次都让主美重选。用户要求“多试几种”“给我惊喜”或项目已经分配探索空间时，在允许变化的维度提出候选。两者可以服务同一个任务，但文件和评审状态分别标明。

先读项目与本次任务的探索预算。已有数量或成本约束优先；没有时建议最多 3 个候选，并明确实际采用的数量、开放维度和用途。预算是本次执行边界，可由已授权的用户调整，不应变成限制创意的永久规范。实际调用收费工具按已有授权处理，不把一个建议数量当成额外消费授权。

参考行为：1 个方向尽量沿用现有制作语言，另外的候选在服装廓形、配色组合或姿态张力上探索。该分配是可选方式，不要求每项日常生产都生成 3 张图。

优秀结果若偏离现行规则，保留原图和观察，填写简短[创意提案](../templates/creative-proposal.template.md)。向主美说明具体收益、偏离和落地代价。它仍可作为候选展示，正式使用时则依据实际决定处理：当前任务采用、有限例外、规范升级或留待以后。身份变化的好图可以是新角色候选，不能因此冒充同一主角合格。

## 从当前版本建立任务

项目运行入口为 `scripts/project_runtime.py`，可来自母 skill 或当前新构建的项目包。先核验收到的包，再在包外建立任务工作区。这些操作由 Agent 执行，不作为用户的操作作业：

| 用户意图 | 运行操作 | 应保留的结果 |
|---|---|---|
| 接入已有项目包 | `init --pack BUILT --out NEW_WORKSPACE` | 项目入口、当前版本指针与发布包副本 |
| 新做一张图或一个资源 | `start WORKSPACE --request REQUEST_JSON` | 原始请求、实际解析的变化、冻结版本、生成任务书和交接要求 |
| 接着昨天那张改 | `resume WORKSPACE --task TASK_ID` | 继续原任务，不自动改用今天发布的版本 |
| 将已决定的新规则供后续任务使用 | `publish WORKSPACE --pack BUILT --expect-current SHA` | 新的当前版本；原版本与原任务保留 |
| 查看本项目现在用什么 | `status WORKSPACE` | 当前版本及任务状态 |

命令中的名字都是实际路径或记录值。`--expect-current` 使用刚读到的当前包指纹，避免两个更新相互覆盖。新建和发布草稿演示时必须显式使用 `--allow-draft`；该选项不把草稿变成正式基线。草稿上的 production 请求会记录阻碍，不能据此继续声称正式生产已成立；可按用户目的做 exploration 候选。

结构化请求包括任务 ID、用户原话、类别、实体或别名、production / exploration、变化槽位、探索范围与数量、责任人。可选 `family` 绑定该类别中的组件/资产家族；`components` 逐项带类别、实体及可选 family，全部沿用同一版本。有家族的类别漏绑时，运行层记录阻碍，Agent 应补齐后另建正确任务。Agent 负责语义整理；脚本校验和冻结请求，不替代自然语言理解或实际制作。

每次 `start` 都重新读磁盘上的当前指针并核验包，随后任务使用自己的固定快照。`resume` 继续固定版本。用户编辑规范草稿后，由 Agent 构建、核验并根据实际授权发布新包；单改文件、聊天里说“记住了”或重新命名旧资产均不构成发布。

独立复制到成员电脑上的旧 ZIP 不会自动升级。团队需要同一项目入口，或明确分发并启用新版本。进行中的批次不静默切换，受影响任务另开新版本批次并检查兼容性。

## 生成任务书后继续做什么

首次接手整个项目或同时交付多类游戏资源时，按 [跨类别交接与组合检查](cross-category-handoff.md) 做新资产和同屏组合。只使用收到的包与本次需求；制作中需要原聊天补充的内容属于交接缺口，应回包升版。相同色板不能代替类型、造型、尺度和状态的一致。

任务目录中的 `generation-brief.md` 是给当前制作环节使用的说明，`handoff.md` 是后续交接说明，`review.json` 起初保留必要检查状态。文件生成意味着任务已准备好，不能代表图片、PSD、Figma 设计稿或引擎资源已经完成。

1. **实际输入参考。** 打开当前身份和风格参考，按各自用途送入图像工具；用已知能力选择编辑或参考图生成。记录真实输入、工具回执和返回文件。工具不提供的模型版本、seed 等保持未知。
2. **生成与选择。** 制作需要的候选或单件图像。使用现有批准设计时可直接制作，不强迫重做概念探索。设计板作为创意依据，正式单件应有自己的输出文件和检查。
3. **分别评审。** 看身份是否延续、变化是否符合请求、风格是否属于项目、文件是否满足已知规格。用[评审指南](review.md)记录具体证据；可变服装按新服装任务检查，不再拿已被替换的默认上衣判错。
4. **准备编辑交接。** 按任务使用 PS、Figma 或指定工具，输出原文件位置、目标画布、锚点、留白、裁切方式、背景、源文件层次与导出要求。未知规格保留未定，不能仅因常见尺寸而代填。需要重排的真实文字使用实际字体和可编辑文字层；字体来源与使用条件按项目实际资料核对。
5. **实际编辑与使用检查。** 有相应工具和授权时执行并保存结果；否则把可执行交接交给成员，保留待编辑或待验证。PNG 不等于有图层的 PSD，改扩展名不构成格式转换，透明通道也不证明边缘在游戏背景上干净。
6. **提交批次。** 将单件文件、真实源文件、评审证据、任务与版本一起交接。使用[团队生产](team-production.md)和批次检查定位漏交、错版、未检查项。批次结构通过不代表艺术批准或引擎通过。

目标环境不同，检查也不同：登录页人物要看实际界面的裁切与文字遮挡；棋子要看棋盘实际尺寸和相邻种类；UI 要看真实文字和状态；动效要播放查看节奏、身份连续性与遮挡；促销横幅要检查商品与品牌身份、活动信息、价格、渠道画布和实际展示裁切；海报要检查对应输出环境的文字层级与阅读尺度。对任务确实要求的工程条件，未执行就记录 unknown，不从概念效果推定完成。

## 负责人只处理值得做判断的事情

成员的普通任务按已有授权继续；不要求设计总监或主美为每一张图重新确认基线。Agent 把需要负责人决定的内容整理成可比较的材料：有争议的身份或风格、值得采用的新方向、会影响他人资产的规则变化、超过既定预算或周期的取舍。

已有明确的决定和授权时直接执行，留下来源即可。没有真实决定时不代签“已批准”。新基线应说明影响哪些角色、场景、UI、商品、版式、动作与外包任务，以及旧资产是否需要返工；不用一张更好看的图自动推翻全项目排期。

## 对成员怎样报告进度

使用业务语言给出四件事：已制作的结果；实际使用的角色与规范版本；已完成的检查；还需要做的操作。必要时附可展开的路径，而不是用一段 CLI 输出作为交付。

示例格式：

> 已准备米拉雨衣招手任务，沿用本任务冻结的项目版本。脸和发型保持角色依据，服装与姿势按本次要求变化。参考输入和输出规格已经整理；图片生成、PS 源文件及活动页面合成检查尚未执行。

只有实际完成对应步骤后才更新这段状态。没有真实图像检查，不报告身份合格；没有必要的工程验证，不报告正式资产交付完成。
