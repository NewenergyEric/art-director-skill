# 大批量素材的团队生产

消除类、休闲游戏、LiveOps 和外包制作常常要同时推进几十到几百个角色、场景、棋子、道具、UI 状态和动效。单张图好看只是起点。真正困难的是让美术总监、内部团队、外包成员和 Agent 在数周或数月里仍像同一个团队。

## 先确认一小批，再展开产量

不要从一份宽泛的画风提示直接铺开全部素材。先挑少量能暴露问题的代表样板：

- 一个主要角色，能看清比例、脸、服装和表情范围；
- 一个完整小场景，能同时看到前景、背景、交互物和 UI 阅读尺度；
- 一组同家族棋子或道具，包含基础款、变化款和特殊状态；
- 一个带反馈的 UI 或动效片段，能看到静止、触发、完成和失败状态。

美术总监确认这些样板后，把确认原因写进规则。团队继承的是“哪些判断成立”，而不是只复制样板表面。

## 把素材看成家族

给每一类高频资产建立稳定的 `family_id`，再说明它允许沿哪些轴变化。常见变化轴包括：

| 变化轴 | 需要说清的内容 |
|---|---|
| 身份 | 哪些轮廓、结构或标识必须保留 |
| 等级 | 从普通到稀有时，复杂度、材质和特效怎样增加 |
| 状态 | 默认、选中、受击、冻结、完成、禁用等状态怎样区分 |
| 朝向与视角 | 正面、侧面、等距或翻转时，哪些信息仍要读得出来 |
| 尺度 | 在棋盘、商店、弹窗和宣传图里分别需要多大的细节 |
| 组合 | 哪些部件可以复用，哪些组合会破坏身份或玩法可读性 |

任务卡至少记录 `batch_id`、`family_id`、本次变化轴、继承的规则、参考 ID、输出规格和负责人。不要靠文件名中的缩写承载全部生产含义。

## 总监和团队怎样分工

| 产线 | 开始前需要什么 | 先看什么 | 批量阶段继续检查什么 |
|---|---|---|---|
| 美术总监 / Lead | 项目意图、代表样板、当前优先级 | 样板是否代表真正方向 | 规则变化、跨产线冲突和例外 |
| 角色与场景 | 画风规则、身份档案、尺度关系 | 角色放进场景后是否仍成立 | 轮廓、比例、材质和叙事焦点 |
| 棋子与道具 | 素材家族、状态表、棋盘阅读尺度 | 同屏时能否快速区分 | 变化是否超出家族边界，缩小时是否可读 |
| UI 与动效 | 信息层级、状态、节奏和实际文案 | 关键反馈是否看得懂 | 多语言、长文本、状态连续性和性能条件 |
| 外包或 Agent | 固定版本的任务包、真实参考和交付目录 | 首件是否理解正确 | 每批输入、输出、修改原因和版本是否对应 |

总监负责方向和取舍。各产线负责人把判断翻译成自己专业里的任务，并把新发现带回评审。Art Director 保存这条往返路径，让“为什么这么改”不会只留在会议里。

## 一批一批地做

1. **冻结本批范围**：写清包含哪些素材家族、数量、状态、格式和所用规范版本。
2. **做首件**：每个新家族或新状态先做一个，确认理解后再复制方法。
3. **批量制作**：使用同一批任务包和命名规则，保留生成、编辑与人工修正记录。
4. **分层抽查**：检查所有代表样板、所有发生规则变化的素材，再加入随机样本和团队主动标出的异常项。
5. **处理偏差**：单件失误回到对应任务；家族共同失误回到样板；项目方向变化才建立新规范版本。
6. **关闭本批**：记录已交付、待修改、未检查和移到下一批的项目，不用一个总分掩盖局部问题。

抽查比例由项目风险、批次大小和交付阶段决定。没有实际检查记录时，不声称整批已经通过。首件失败时先修正理解，再继续生产；继续生成更多同类素材只会放大返工。

## 交付时留下可继续工作的东西

一个批次结束后，应能找到：本批任务卡、所用项目版本、代表样板、素材清单、实际输出、逐项评审、返工原因和下一批新增的判断。文件名、目录和清单使用稳定 ID；展示图可以讲故事，生产文件仍要能被脚本和引擎可靠读取。

当新反馈只影响一个素材或一个批次，把它留在局部任务里。只有影响多个家族或后续生产的共同判断，才提出规范变更并进入版本流程。
