# 参考驱动的制作与验收协议

用于按参考续作、跨题材延展、首件校准，以及“过度精致”“不像项目里的东西”“放进实际界面不合适”等修正。它补充现有总监、成员和评审流程；项目判断仍写入 `style-pack.json`，不另建一套规则库。

## 先确定用途，再决定画法

从已有项目和用户当前要求得到五件事：做什么、用在哪里、继承什么、可以改变什么、怎样检查与交付。缺少正式参数时可以提出本轮试验假设，记录依据；不把猜测写成正式规格，也不为非关键缺口反复打断制作。

类别按用途选择。微波炉可以是场景 `prop`，也可以是消除游戏的 `tile`；物体名称不能决定交付方式。用户从“整组食品”改为“一个新电器”时，更新当前范围并把旧清单标为已替代，继续沿用仍有效的画风要求。

输出分辨率、主体在画布内的大小、最终显示大小是不同条件。清晰导出不要求增加纹理；正方形画布也不证明物体适合一格。

## 主美建立可以被复用的判断

对当前参考明确以下边界，优先描述可见事实；只有实际测量或已有规格支持时才填写数值：

| 判断 | 要保留或限制什么 | 不应顺手增加什么 |
|---|---|---|
| 轮廓与结构 | 大形比例、识别部件、层数与转折 | 多余零件、装饰和夹层 |
| 厚度与空间 | 体积夸张、折叠程度、视角和深度 | 厚褶皱、过深凹槽、夸张透视 |
| 表面表达 | 材料靠色面、笔触还是纹理区分 | 参考没有的毛孔、纤维、颗粒和刻线 |
| 明暗与高光 | 光向、对比、阴影与反光的职责 | 广告式反射、镜面高光、额外发光 |
| 实际使用 | 主体大小、背景关系、状态与邻近元素 | 为单张展示增加的底座、场景和无用留白 |

简化不是默认风格；细腻写实项目可以要求更多细节。标准来自当前项目，不能把某次失败变成所有资产的低细节上限。premium、cinematic、intricate、3D render 等词必须服务已确认的表现目标，不能当作自动美化前缀。屏摄摩尔纹、噪点、压缩模糊和编号不作为画风继承。

不同题材延展时，继承比例处理、边缘、色域、明暗与材料表达；重新设计新对象的识别结构。不能把食物的层状结构搬到电器上，也不能因题材变化重新发明画风。将继承范围与新对象变量说清楚即可，不要求用户再次描述整套风格。

## 让这些判断进入团队包

| 已有位置 | 写入的内容 |
|---|---|
| `rules` | 有理由、适用范围、参考依据和确认状态的复杂度与使用要求 |
| `profiles` / `direction.families` | 该类别或家族的固定项、允许变化、技术条件 |
| `references` | 风格、身份、构图、上下文或反例各自负责什么；不继承什么 |
| `direction.exemplars` | 代表样板的实际文件、覆盖范围、验收情境及真实决定 |
| `direction.delivery` | 导出、源文件、使用检查及团队实际交付要求 |
| `decisions` / `open_questions` | 变化来源、已确认范围与仍未定的条件 |

自然语言约束进入规则或固定项；画布、格子、锚点等进入适用的 `technical`。本次尝试次数、目标物件和生成参数留在任务记录。不要为套模板把所有字段都填满。

母 Skill 的更新不会改写已发出的 ZIP。新构建的项目包应携带执行方法；要应用新要求，从工作副本升版后重新构建、核验和分发。旧任务保持快照，迁移依据现有授权处理。

## 成员先做一件可检查的结果

1. 读取当前任务的固定版本与适用规则。已有认可样板可以复用，不把日常制作变成重新选风格。
2. 实际打开参考，并按角色送入工具。原参考负责画风；修正对象负责必要身份；反例只说明不要什么。提示词中的路径不等于真实图像输入。
3. 写清“本次改变、必须保留、不能增添、显示用途”，再生成或编辑独立素材。工具未提供的参数保持未知，保存原始输出。
4. 用实际输出与参考检查简化边界和使用效果，再决定是否扩量。不要先生成整批，最后才发现首件不适合目标位置。

同题材比较应固定使用尺寸和相近的可见主体尺度，避免靠缩小复杂稿掩盖差异。跨题材比较共同视觉语言，并另外检查新对象是否易认；不存在同题材参考时如实说明。

## 棋子在格子里验收

适用于 `tile`，具体格数、像素数和占比由项目决定：

- 明确单格或多格占位，在实际或注明的试验格子中看完整轮廓、可见大小、视觉重心、关键部件与边界。
- 用真实预览缩放方式查看；在参考比较中保持主体尺度，在使用检查中保留交付文件自身的画布和留白，不能只裁剪预览以掩盖资产问题。
- 将同一棋子相邻重复，再与已有种类、必要的等级和状态混排；检查间距、辨识与遮挡。差异不能只靠颜色。
- 识别特征过小时减少次要细节、调整必要比例；不要仅扩大图片导致越格，也不为占满方格强迫所有物体变方。
- 透明图在适用背景上看边缘；有 alpha 不代表轮廓干净。静态合成应标为示意，不能称为游戏运行或设备验证。

UI、场景、角色等类别仍检查各自的真实用途；不用棋盘要求约束无关类别。

## 反馈改变了哪一层

| 反馈 | 先查什么 | 本轮修正 |
|---|---|---|
| 过度精致 | 结构、厚度、纹理和高光分别是否超出参考 | 修改偏离项，不只去纹理 |
| 不像同一个对象 | 身份参考是否实际输入、固定特征是否丢失 | 恢复身份，保留已授权变量 |
| 放进格子看不清 | 画布留白、有效大小、识别部件、背景与邻格 | 调整格内效果，再复查相邻排列 |
| 大图统一、组合不统一 | 实际尺度、光照、视角、焦点与密度 | 修组合关系，不只统一色值 |
| 连续修正仍重复同样错误 | 失败稿是否继续充当正向风格参考 | 返回原参考或只保留必要身份输入 |

每轮记录“问题、改变、保留、实际结果”。错误结构持续时改变参考或制作方法，不能无止境追加“更简单”的形容词。遵守当前任务预算和既有修正检查点；满足任务就交付。共性规则缺口回项目工作版，单件瑕疵只修该件，候选新方向保留为提案。

需要把判断教给其他成员时，使用[图解卡、整链设计与返修对照](visual-judgment.md)。减少细节时同时说明仍需保留的体积、识别和功能；修后在对应使用条件下复查保持项。整组扩展先设计共同继承和各成员的可辨差异，不能把单件合格等同于整组成立。

## 交付时分清事实

交付本次选定文件、实际使用的提示/工具输入、版本与检查证据。过程稿留在工作记录中，交付包按用户需要保持精简；不混入已替代任务的“待交付清单”。

技术实测、视觉自查、实际使用验证和主美决定分别报告。不能用文件校验代替画风判断，也不能把自查写成负责人批准。最终设备或引擎未测时保留范围说明，不阻止已有授权下的候选交付。

使用[首件记录](../templates/game-art-first-article.template.md)保存关键证据即可；已有任务书与评审记录能够承载时，不再复制一份完整表格。
