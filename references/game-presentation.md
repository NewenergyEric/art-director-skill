# 把游戏内容做成宣传画面

用于商店截图、README 动图、项目介绍与宣传视频。先沿用项目的视觉规范和真实资产，再决定传播构图；不要给所有游戏套同一种描边、绳结或配色。

## 先看用户会看到什么

读用户指定商店页的实际图片，记录标题在卖什么、角色动作、前中后景、界面与道具的关系。区分可借鉴的表达方法和不能当成自己项目素材的角色、标识、剧情。不能只读页面文字就声称完成了视觉研究。

一幅画面只传达一个具体结果。把“连续场景状态验证”翻成“修好栈桥，故事继续”，让修缮、动作和奖励本身支撑标题。技术说明、限制与复现入口放在画面外的正文，不能用大量字幕代替缺少的内容。

## 文字也是资产，但仍须可读

- 主标题用项目适合的字重、倾斜、轮廓、描边、填色和厚度设计。汉字描边须实际渲染，检查笔画相交处是否出现白线、空心或糊成一块。
- 标题优先压在有意预留的画面空间中；人物和道具可以跨框，但不能遮住脸、手、主标题或关键操作。
- 小字、安装步骤、正文与界面数值保持正常可读字体。准确文本保留可编辑来源；不能把生成图片中的错字当成完成品。
- 需要木牌、按钮、绳索或装饰框时，从项目的材料与轮廓出发制作独立透明元素。不要把整张宣传图冒充可编辑拆层。

## 让构图说明关系

避免连续采用“左侧讲解＋右侧手机截图”和三张等宽卡片。按用途切换满幅场景、角色前景、道具链、真实界面局部、修复对比或连续故事；统一视觉语言不等于重复布局。

效果服务事件：两件道具靠拢后升级、交付后资源变化、修缮产生接触扬尘、点灯改变光照、归船带尾迹。不能只给所有图片加悬浮动画。剧情、界面数值和操作必须能追溯到实际原型或标清为宣传示意。

最后看真实导出：缩略图标题能否读懂；同一段的画面是否支持标题；裁切是否漏掉主角或归船；放大后文字与 alpha 是否干净。MP4、GIF、静态备用图与网页要从同一来源更新。视觉观察、自动检查和用户认可分别记录。
