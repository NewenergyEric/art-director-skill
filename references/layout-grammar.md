# 信息型 UI 的布局语法

版式先说明信息关系，再承载风格。不要从“做几个卡片”开始；先问用户第一眼要看懂什么、哪些内容需要持续可见，以及位置是否代表状态、时间或空间。

| 布局 | 适合表达 | 可执行约束 |
|---|---|---|
| **Hero Module · 主次布局** | 一个结论、任务或主画面明显高于其他信息 | 主模块至少占首屏一半；次要指标缩成小块贴右侧或下方；第一视线只能有一个落点 |
| **Stacked Bands · 横带分层** | 概览、趋势、明细存在自然的阅读顺序 | 全幅切成三条通栏横带；每一带只回答一个层级的问题；从上到下完成“结论 → 变化 → 证据” |
| **Main + Aside · 主区加窄栏** | 主内容持续滚动，同时需要日程、提醒、状态或证据常驻 | 主区约占三分之二；侧栏保持 280–340 px 并可粘性定位；侧栏不能抢走主任务的视觉焦点 |
| **Full-bleed Canvas · 全幅画布加浮动面板** | 地图、大图、关系图或空间本身就是主要内容 | 画布铺满主区；数字和列表只浮在四角或空白区域；面板数量要少，不遮挡关键关系 |
| **Kanban Columns · 看板分列** | 位置本身代表状态，内容需要跨状态移动 | 状态列等宽；列头显示名称与计数；允许横向滚动；同一张卡只处于一个明确状态 |
| **Timeline Swimlanes · 时间轴泳道** | 任务有起止时间、并行关系、依赖或冲突 | 顶部共享时间刻度；每条泳道画真实起止横条；当前时间用竖线标记；缩放后仍保留冲突提示 |

## 选择规则

1. 只有一个绝对重点时，用 Hero Module；不要让多个“大卡片”彼此争夺主位。
2. 用户要沿阅读顺序逐层理解时，用 Stacked Bands；不要用它表达频繁横向比较。
3. 辅助信息必须持续可见时，用 Main + Aside；移动端把窄栏放到主区之后，不压缩成无法阅读的小列。
4. 空间关系比数字更重要时，用 Full-bleed Canvas；浮层需要避开主体，并提供展开后的明细入口。
5. 状态变化是核心时，用 Kanban；若重点是截止时间和冲突，改用 Timeline Swimlanes。
6. 一页先选一种主语法。可以在局部嵌入第二种，但要说清谁负责整体结构，谁只负责一个模块。

## 写进任务书

布局选择至少记录：主目标、首要视线、区域比例、滚动方式、持续可见内容、移动端退化方式，以及不采用其他布局的具体原因。把“高级感”“大气”改成可观察的构图决定，例如“首屏主模块占 60%，右侧 320 px 窄栏固定显示审核状态”。
