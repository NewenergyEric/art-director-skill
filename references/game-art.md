# 游戏美术的任务拆分

项目风格规则控制同一世界的视觉语言；实体记录控制“还是不是同一个角色或物件”；本次任务控制动作、用途和构图。不要把这三类约束混为一张画风提示词。

## 先固定本次任务的坐标

读取 `scope`、相应 `profiles`、实体与适用规则，确认资产处于概念探索、生产设计还是引擎交付阶段。对未知的媒介、视角、平台或制作要求写明未定。不要依据“游戏美术”擅自选择 2D、3D、等距视角或某个引擎。

只收集会影响当前阶段的规格。概念探索通常需要用途和阅读尺度；引擎交付需要对应工程约束及真实导入检查。

| 类别 | 风格与身份的关键问题 | 任务允许变化 | 需要实际验证的条件 |
|---|---|---|---|
| 角色 `character` | 比例与轮廓、脸部与发型身份；默认服装与不可变身份分开；阵营、职业及装备连接 | 已允许的服装、姿势、表情、镜头、状态 | 实际游戏尺度辨认；需要时检查多视图、动作连续性与装备遮挡 |
| 场景 `environment` | 形状与建筑语汇、材质风化、空间尺度、焦点与导航 | 地点组合、时间天气与区域差异，服从项目约定 | 角色与环境尺度、可行走区域可读性、前中后景、模块接缝 |
| 棋子 `tile` | 颜色和形状身份、轮廓、描边、普通/选中/特殊状态编码 | 已约定的状态反馈和等级变体 | 实际棋盘尺度、同屏识别、状态区分与缩放后的留白 |
| 道具 `prop` | 用途、握持或使用关系、材质语言、与角色及世界的比例 | 被允许的磨损、等级、颜色或装饰变体 | 缩小时能否识别；需要时检查支点、碰撞、交互与装配 |
| 字体与 UI `ui` | 字形气质、文字层级、图标语汇、状态与视觉焦点 | 内容长度、语言、可用空间、项目规定的反馈状态 | 实际尺寸、长文本和多语言、必要字符、交互状态及对比度目标 |
| 动效 `motion` | 继承源对象身份、节奏与强弱、视觉焦点和遮挡边界 | 已允许的形变、轨迹、时序与反馈阶段 | 真正播放后的衔接、目标棋盘/界面遮挡；需要时检查引擎时序与性能 |

这些是选择检查项的菜单，不是默认增加的硬规范。例如“背景必须低饱和”“只能三种色相”“角色必须几头身”都只能来自项目决定。

外包通过责任人类型和交付协议管理，沿用实际资产类别与同一规范；不要新增一个不受角色、棋子等规则约束的“外包风格”。多工种并行和批量验收见 [团队持续生产](team-production.md)。静态动效分镜属于设计提案，不能冒充已验证的可播放资源。

## 2D 与 3D 分开定义“完成”

**2D**：视用途确认画布、透明背景、裁切与留白、基点、方向、动画帧/状态、图集边距及分层源文件。像素美术需明确像素尺度和缩放方式，只有已经确定时才规定抗锯齿方式。立绘不必承担精灵动画的检查项。

**3D**：区分概念参考、多视图设计、实际网格与材质交付。只有项目生产链已明确时，才检查单位、轴向、拓扑、UV、材质通道与色彩空间、贴图规格、骨骼、LOD、碰撞和性能预算。生成图、渲染图和三视图都不能代替可编辑模型或引擎验证。

渲染器、光照环境、后处理、相机和曝光会改变资产的可见风格。记录已使用的条件；不能因两张图的展示光照不同就直接认定材质规范冲突。样板可同时保留中性观察图与目标游戏环境中的效果图。

## 角色和关键道具的身份管理

给需要跨任务保持一致的对象稳定 ID，在 `entities` 中记录：适用类别、身份参考、必须保持的特征、允许变化和相关说明。不要只用“长得像参考图”描述身份。

可观察的身份特征例如刘海分束、脸部轮廓、固定标识或工具关键结构。衣襟、腰挂物、护甲连接可能属于某套服装而不是角色永久身份：若任务换装，应读取其槽位范围与默认值。不要为了保脸把每件衣服都锁死，也不要因为换衣解除脸部要求。以实际已确认材料为依据；不可见的背面细节仍是未定设计问题。

收到“换个角度，但还是原主角”时，先加载该角色的身份图，再加载项目画风参考。身份一致性与风格一致性分别评审。一张主参考未必包含所有视角，不得用它声称已证明背面或运动中的身份一致。

## 字体与图中文字

记录字体家族、用途、回退与来源；没有可用字体文件或许可信息时明确未定。风格上像某字体不等于实际使用了该字体。涉及确定的中文、数字或 UI 文本时，优先采用可编辑排版层并按真实字符串检查，不能把生成图中的近似字形验收为正确文本。

文字可读性应在目标显示尺寸检查，装饰标题不能自动决定正文规范。若项目采用无障碍或对比度指标，写清适用标准及场景，再做对应技术验证，不凭印象声称合规。

## 制作任务书的最小内容

任务书应足够让另一位成员独立工作：项目版本、类别、实体、用途及交付阶段；本次目标；已确认的硬要求和建议；固定项与可变项；按用途列出的参考；已知技术规格；尚未解决的问题；输出清单和验收证据。

使用 `brief` 编译后仍需核对实际任务。编译只负责忠实汇总，不会替总监确定风格，不会自动得知新模型的最佳参数，也不证明参考图已被生成工具接收。

组合画面同时包含人物、道具和场景时，分别读取这些类别或分别编译任务书，再合并适用规则并去重全局项。不能只选一个主类别就忽略画面中其他资产的约束；实体身份仍绑定各自对象，不把所有角色的身份图混在一起。

首次采用一个项目包，可让不同成员或独立会话制作少量同类及跨类别任务，比较执行的规则和返工原因。记录任务、版本、工具、输入与评审；没有实际用户和生成结果时，只能报告规范与工作流验证，不能声称团队一致性已获得证明。
