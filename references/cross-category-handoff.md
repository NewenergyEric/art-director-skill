# 一份视觉记忆，怎样交到下一位手里

用于主美完成第一版方向、团队第一次拿包试做，或用户指出“颜色一样，但不像同一款游戏”的情况。一次完整试用要看到成员新做的资产及真实组合，不能仅靠把样板重新排一张板。

## 先确认它属于哪一种游戏

先看实际玩法画面，把宣传插画、剧情角色、地图场景、棋盘物品和 UI 分开。记录目标画面里每类资源的显示尺寸、镜头、信息职责和细节量。一个漂亮的宣传主视觉不能直接充当所有类别的制作标准。

以休闲合成游戏为例，应观察棋盘格内的物品占比、相邻等级轮廓、生产器/可合成物/订单需求的区别、订单与资源栏的位置、选中/缺件/可提交的反馈。把观察转成该项目的候选要求；不要把某个竞品的格子数量、按钮颜色或数值当作类型标准。不能只摆几件道具就声称做出了合成游戏界面。

## 主美留下哪些具体判断

用项目已有资料写出四层内容，回写 `style-pack.json`，手册由它生成：

1. **共同语言**：大中小形、主次色、明暗和材料处理；同时写清哪些细节应省掉，以及为什么。
2. **类别翻译**：角色用什么比例与线面，场景用什么镜头与空间，物品在格内怎样识别，UI 如何分清信息与操作。共同语言在各类别里的实现可以不同。
3. **具体身份与结构**：角色脸与发块、建筑门窗和地面位置、物品等级轮廓、组件区域与状态。能变的动作、修复状态或文案另列为变量。
4. **组合接口**：每件放在哪里、以多大尺寸显示、脚底/底座/对齐点在哪里、谁遮谁、文字由谁排，以及拿哪些实际文件进行组合。

摄影感、大片感、精致、高质量等词不能替代这些判断。单次宣传图的“手接触灯、背后有灯塔”只属于该任务构图；不要把它写成所有角色和所有场景都必须满足的硬规则。

家族共同规则放在类别或 `direction.families`；只有某个对象自己的特征才写进 `entity.identity_rules`。否则新增成员没有绑定旧实体时，任务书会合理地排除旧实体规则，连同误放进去的家族要求一起丢失。

## 首批包至少带上什么

围绕本次实际分工准备样板，不强求固定张数：角色身份图、场景结构图、物品家族参考、带真实文字的 UI 或组件状态。没有相应样板的类别明确列为待建立。UI 若交付 HTML/CSS、SVG 或其他源文件，把字体、图片和依赖一并收进包；只有截图不能证明可编辑交接成立。

每份样板说明“参考什么、不参考什么”。主视觉可以解释色彩和世界，不能自动定义角色转面、等距镜头、所有道具视角或 UI 排版。候选样板仍是候选；本次获准试做不等于项目已完成主美生产验收。

## 用收到的包做一次新任务

将包构建、压缩、解压到一个新的工作目录，再使用包内入口与工具开始任务。制作输入只能来自收到的包及本次新需求。不要临时去原聊天里补一张身份图、从主美电脑找字体或另写一套没有回包的画风提示词。发生这种依赖就记录缺口，修包、升版、重发，再重开受影响任务。

按本次范围至少覆盖角色、场景、UI 和物品家族各一项有实际变化的工作。例如同一角色的新表情/动作、同一地点的修复状态、新订单及缺件/可提交状态、家族的新成员。每项保留实际输入图、原始输出、定向修改、导出文件与检查。旧图改名不算成员续作。

若由同一个 Agent 模拟不同职责，要如实称为“隔离目录的交接自测”；不能声称独立人员盲测或真实团队使用。通过文件快照和输入清单减少对原上下文的依赖，但不能证明模型已忘记原聊天。

## 验收要把东西放到一起

先分别检查，再把实际新资产放进约定的游戏画面。逐条写观察及结果，避免只给一个笼统总分：

| 范围 | 至少要看见的证据 |
|---|---|
| 角色 | 基准与新动作并排；脸、发块、比例、身份装饰保持，允许变化真的发生 |
| 场景 | 同镜头前后对照；建筑结构、透视、交互区和角色尺度，修复只改授权部位 |
| 物品 | 相邻等级缩到目标格内；轮廓、材质、镜头、光源、有效占比和背景边缘 |
| UI | 真文字、长文案及任务要求的状态；选中/禁用/可提交可区分，按钮与物品不互相抢占 |
| 组合 | 使用相同版本的实际输出；检查焦点、尺度、遮挡、密度与共同世界观 |

透明图需查看实际 alpha 合成。查看器把 alpha=0 的 RGB 色晕显示出来，不代表游戏中真的存在色晕；反过来，存在透明通道也不代表边缘干净。给出浅/深背景证据，不能靠猜。

失败只修对应问题：缺身份图就补身份依据，轮廓太细就重做形状，UI 少状态就补组件状态；共性问题回写规范，单件瑕疵只返修该件。候选通过视觉自查、文件通过校验、玩法原型能运行、引擎能导入、主美批准是不同结果，分别报告。

## 界面也要有自己的美术资产

用户说“像 PPT”时，先比较游戏画面里的内容职责与制作方式，不能只加渐变或把卡片变圆。按该项目玩法列出实际资产：角色订单、资源图标、生产器、可合成物、阻挡物、奖励、状态标记、按钮皮肤与说明区。每个图标连接一个真实状态或操作；无需为画面密度虚构无效按钮、充值或活动入口。

把文字也写进规范：标题、数值、正文分别用什么字重、描边或阴影，哪些位置需要紧凑、哪些需要安静。手绘或有体积的资产与原生可编辑文字组合；不要把不可编辑的生图文字当成完成的 UI。排版要看长文案、禁用对比、触摸尺寸、缩小阅读及遮挡，不能只验收无字底图。

在目标视口检查画面裁切：横版地图铺满竖屏时，屋顶、门窗或交互点可能消失。记录图像比例、裁切许可、安全区和角色锚点；需要竖版时另做适配样板，按版本重发。没有规格依据，不要靠 object-fit:cover 或随意放大立绘补救。

丰富度来自玩法关系，不以元素越多越好。把资产放在真实密度下，操作一次生产、合成、交付与后续反馈，检查数值、图标和状态一致变化。原型验证与引擎、商业数值、长期体验分别记录。

可复用 UI 在独立页面与嵌入介绍/影片后都要检查。组件容器应声明自己的字体与文字颜色，避免宿主的浅色标题样式让奶油面板上的文字消失。字体子集要覆盖新增文案；看见字体加载成功，不等于所有新字都有字形。
