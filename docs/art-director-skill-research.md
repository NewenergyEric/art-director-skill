# Art Director Skill：游戏美术团队的风格管理需求与参考调研

调研日期：2026-10-09（北京时间）。当前阶段：需求与架构提案。第一验证场景已确定为游戏美术，覆盖人物、场景、道具、字体与 UI。

本次查阅了 GitHub 原始 SKILL.md、配套模板、部分目录、许可证及仓库版本信息；没有安装这些项目，也没有实际运行其生图或评审流程。下文明确区分仓库已有内容与我们建议实现的能力。

**产品定位：把美术总监的审美意图，转成团队及其 agent 能共同使用、验证和更新的项目美术规范。** 总监通过交流、参考图和样板评审建立标准；成员在各自的会话中加载同一份项目包，继续设计、生成和检查资产。

核心价值应体现在：总监不用对每个人重复解释，成员遇到新资产也能根据设计理由作出相近判断，返工意见能够积累为后续工作可用的知识。

**建议采用“母 skill → 项目风格包”的结构。** 母 skill 帮总监建立、校准和维护规范；它生成的项目风格包包含一个可调用的项目 skill，以及规范、参考资产、生产配方和验收标准。团队收到整个包后，应能在没有总监原始聊天记录的情况下开展工作。

```mermaid
flowchart LR
    A[总监的意图与参考] --> B[母 skill 提炼规则]
    B --> C[样板资产与组合画面]
    C --> D[总监确认项目基线]
    D --> E[发布项目风格包]
    E --> F[成员及 agent 制作资产]
    F --> G[按规则和画面评审]
    G -->|修正资产| F
    G -->|提出规范变更| D
```

**首先把“一致性”拆成几种不同的问题。** 一套色板无法同时解决这些问题，统一提示词也不足以覆盖它们。

| 一致性类型 | 游戏中的例子 | 项目包需要提供什么 |
|---|---|---|
| 审美意图一致 | 古老但有人生活，温暖但不幼稚 | 视觉目标、设计理由、取舍顺序、正反例 |
| 画风一致 | 人物、树木、武器具有相容的造型和材质表现 | 形状、边缘、明暗、材质、细节密度规则 |
| 身份一致 | 同一角色换姿势后仍是同一个角色 | 角色设定图、身份特征、服装和配饰约束 |
| 系列一致且有区别 | 同阵营的不同职业既同属一族又可辨认 | 共享规则、职业差异、允许变化的范围 |
| 游戏画面一致 | 角色不会淹没在场景中，道具和 UI 不争抢注意力 | 实际视角、显示尺度、背景、组合画面及可读性检查 |
| 交付一致 | 文件尺寸、透明通道、资源命名与导入设置正确 | 资产类型规格、确定性检查、目标引擎要求 |

总监负责决定意图和发布基线；设计师负责在允许范围内创作、提交结果与发现规范缺口；技术美术负责把视觉目标接到真实生产条件。agent 可以辅助上述工作，但文字中的角色设定不构成实际权限系统。

用户口述的“花书”对应找到的是花叔的上游仓库 alchaincyf/huashu-design；“Zala 张”很可能指 Zara Zhang 的 frontend-slides。这里使用作者仓库，未采用翻译版或技能合集镜像作为主要依据。

**我们需要把交接和后续维护做成完整流程。** 现有参考已经覆盖不少美术知识和制作步骤，因此不宜把差异简单定位成“一个 AI 美术总监角色”。更有价值的组合是：审美判断提取、项目包生成、跨会话复用、基于证据的评审，以及受控的规则更新。

1. **收集真实项目上下文。** 接收已有概念稿、喜欢与不喜欢的参考、角色设定、游戏截图、字体和材质样本。同步记录 2D/3D、视角、目标平台、实际显示尺度及目前需要制作的资产。已有规范先继承；缺少信息时区分“待总监决定”与“可以临时提案”。
2. **将审美词语转成可比较的选择。** 围绕关键分歧展示小样，例如同一个道具的三种材质处理。记录总监选择的理由及否定的具体部分。方向已明确时可直接进入样板验证，不必固定要求每次都提供三种风格。
3. **建立有代表性的样板组。** 人物、环境片段、道具和 UI 字体样例应能放在一个画面里检查。单张漂亮的主视觉不足以证明风格能跨类别使用。不同参考承担不同作用，身份参考与构图参考尤其要分开。
4. **确认并发布项目包。** 将已确认规则、样板、类别规格、评审依据和工具配方形成一个可完整复制的版本。未定项明确保留为未定，不能由 agent 悄悄补成总监的选择。首次基线和共享规则变更由总监或其授权者确认；日常制作沿用已授权的范围。
5. **成员制作、评审与修正。** 加载当前任务指定的项目包版本，提取适用规则，选择参考图和生产方式；生成或手工设计后附带交付记录。评审指出依据、位置、偏差和修正建议。反复出现的规范缺口形成变更提案，再由总监决定是否发布新版本。

**项目包需要让人能理解，也让 agent 能执行。** 以下是建议的数据结构，尚未生成或安装实际 skill；样板文件只有在获得真实材料后才会创建。

```text
art-director/                        母 skill：建立、校准、打包、维护
  SKILL.md
  references/                       各阶段的方法和游戏美术类别指南
  templates/                        规则、参考索引、交付与评审的模板

project-art-style/                   母 skill 生成，整个文件夹交给团队
  SKILL.md                          何时调用、如何制作、如何检查
  pack.yaml                         项目、规范版本、状态、兼容能力
  rules.yaml                        规则的权威记录
  art-bible.md                      面向人的说明，由同一批规则生成
  references/
    index.yaml                      图片用途、适用对象、来源、确认状态
  assets/
    anchors/                        总监认可的样板图
    counterexamples/                已标注问题的反例
    fonts/                          项目可分发时附带实际字体
  recipes/                          已验证的工具或模型生产方式
  review-rubric.md                   从规则导出的检查方式
```

规则不应在多个文件中各自维护。规则 ID 连接机器记录、可读说明和评审依据；修改规范时同步重新生成相关内容。运行时只读取共享规则与当前资产类别，不把所有类别、全部历史和全部图片一次性塞入上下文。

生产输出存放在项目工作目录中，不写回已发布风格包。每次交付记录资产 ID、项目包版本、使用的参考 ID、生成或编辑工具、可获取的模型版本与参数、检查结果，以及人工确认状态。工具没有返回的字段标记为未知，不编造 seed 或模型信息。

**规范的关键是同时表达“固定什么”和“允许怎么变化”。** 一条规则建议包含 ID、适用范围、要求、设计理由、约束强度、可变范围、参考证据、检查方式与确认状态。数值范围需要来自项目决定或实际样板，不能为了显得精确而虚构。

| 类别 | 要确认的内容 | 允许变化的例子 |
|---|---|---|
| 全局视觉 | 造型语言、明暗组织、边缘处理、材质表现、细节层级 | 不同区域的局部情绪与配色 |
| 人物 | 比例、轮廓、身份特征、服饰构成、阵营识别 | 职业装备、表情、姿势和角色个性 |
| 场景 | 空间比例、建筑构件、前中后景关系、背景信息密度 | 地貌、天气、时间与叙事状态 |
| 道具 | 形状家族、功能可读性、材质与磨损规律、尺度 | 用途、等级、使用者与稀有度 |
| 字体与 UI | 实际字体资源、字重、字号层级、语言覆盖、图标笔触 | 标题、对白、数值和交互状态的层级变化 |

示意项目“苔港”的总监说：“要古老、温暖，但仍然有人生活，旧而不脏。”这句话可以经总监确认后拆成：常用接触位置有磨损，维护过的构件保留较整洁表面；人物装备的细节体现职业；背景不以满屏污渍表达年代。新加入一座磨坊时，设计师能据此推导出维护痕迹，而不只是重复某一张旧房子的配色。此例是需求示意，不是已确定的项目风格。

**执行时必须区分项目画风与对象身份。** 场景参考只负责画面组织时，不应把其中陌生人物的服装带进已设定的主角；角色设定图负责身份时，也不必把它的站姿复制到每一次输出中。参考索引要写清各张图的用途、影响范围和优先处理的冲突。

生成配方应将共享规则、对象设定、本次变化与技术要求分开组织。实际调用时必须传入工具可访问的图片，而不仅是在提示词里写一个本地路径。缺少图片理解、参考图编辑或生图能力时，交付规范、制作任务书与待执行步骤，并准确说明哪些视觉检查尚未完成。

**图像生成能力需要单独适配。** 例如 [Tencent IP-Adapter](https://github.com/tencent-ailab/IP-Adapter) 提供以图片配合文字引导扩散模型的机制，可以作为研究参考图约束的技术来源。它是生成侧组件，不是团队风格管理 skill，也不保证任何模型、任何任务都能保持角色身份。首版应使用团队已有、支持参考输入的工具做基线实验，再判断是否需要更复杂的工作流。

同一提示词或同一 seed 不应被当成一致性保证；更换模型、版本或工作流后，应重新检查样板任务。图像参考、项目规则、工具配方和结果评审共同构成我们的验证方案，实际有效程度需要试点确认。

**评审需要产出可操作的差异，而不只是一个分数。** 建议分开记录以下三层结果：

| 检查层 | 可以怎样验证 | 结果如何表达 |
|---|---|---|
| 文件与规格 | 文件存在性、尺寸、格式、透明通道、命名和必需记录 | 通过／失败及实际读取值 |
| 视觉与语义 | 对照样板看身份、造型、材质、层级；在目标画面中看协调程度 | 具体位置、规则 ID、参考图、偏差、修改建议；无法判定则标记待确认 |
| 总监的艺术判断 | 意图是否成立、例外是否值得接受、规则是否需要改变 | 接受、修正或规范变更决定及理由 |

例如：“左肩甲的镜面高光偏离 MAT-02 的粗糙金属样板；降低高光锐度，保留现在的轮廓和职业标识。”这样的反馈比“风格相似度 87 分”更能帮助下一次制作。该句仍是假想示例，并非对真实资产的评审。

二维概念图、可导入资源和实际游戏中验收通过的资源应分别标识。生成图不能证明网格、UV、骨骼或导入设置正确。字体规范需要落到真实字体及排版方式，不能靠模型在画面里画出的字证明字体可用。

**版本管理要让团队知道自己正在用哪套标准。** 一项任务开始时记录项目包版本，制作中不自动切换。成员可以提出新规则或特例；共享版本的修改经过明确发布流程，并说明影响哪些资产。已通过的产出只有经确认后才加入样板库，避免逐轮把偏离的衍生图变成新标准。

首版可以用文件夹或 ZIP 交接，配一个简单的发布记录。共享仓库或资产库可以后续加入。发布权限依赖实际的仓库、存储服务或人工流程；写在 SKILL.md 里的“只有总监可改”不能替代访问控制。

**首版 MVP 应验证完整交接，而控制资产范围。** 建议选择一个已有视觉材料的小型游戏项目，在同一视角、同一生成工具与固定流程下先跑通：

| 阶段 | 具体交付 | 通过条件 |
|---|---|---|
| 定义 | 审美访谈、规则初稿、参考图用途说明 | 总监能指出每条关键规则是否准确表达意图 |
| 校准 | 代表性人物、场景局部、道具、字体 UI 组合样板 | 放在一起时，总监认可它们属于同一项目 |
| 打包 | 可独立加载的项目 skill 与完整资源包 | 新会话无需原聊天记录即可找到有效规则和参考 |
| 生产与评审 | 多人分别完成同一组测试任务 | 交付记录可追溯，偏差反馈能用于实际修改 |

建议测试集：2 个角色姿势或状态、2 个场景局部、3 个道具、1 个字体/UI 组合画面，共 8 项。先做二维概念与视觉样板；如果试点项目是 3D 游戏，同期记录其生产约束，网格与引擎交付验证随后单独接入。这是建议范围，尚未替用户决定具体引擎、模型或美术风格。

试点可请 3 位设计师分别在全新会话中完成同一任务集。每人比较“当前团队常用材料”与“项目风格包”两种条件，尽量固定模型、生成次数、时间预算和参考资产可获得性，交错安排任务顺序以减少熟悉度影响。这样的对照优先衡量规范与流程的增益，再追加更换 agent 或工具的兼容测试。

记录首轮可接受率、修改轮次、总监评审时间、身份偏差次数、跨类别协调问题和新成员启动时间。由总监打乱顺序评审；小样本结果只用于判断试点是否值得继续，不包装成普遍有效的统计结论。先获取基线，再决定目标，不预先承诺一个漂亮的提升百分比。

**首版还需要验证几个容易被忽略的行为。** 成员请求超出规范的新区域时，系统能否合理推导并标出未定项；参考之间矛盾时，能否说清冲突；缺少图片时是否承认无法检查；切换项目时是否避免带入上一项目的规范；规则升级后是否仍能复现旧任务依据。这些情境比检查文档是否有指定标题更有意义。

目前已经确定目标用户、核心任务和游戏美术优先级。正式实现前仍需由真实项目补齐：首个试点的 2D/3D 与视角、现有样板和返工案例、常用生成/DCC 工具，以及团队如何接收项目包。它们不会阻碍当前架构设计，但会决定第一套生产配方和验收方式。

**后续扩展可以保留同一套建立与交接流程，替换领域规则。** 平面和海报更关注版式、品牌资产和多尺寸物料；建筑效果图更关注空间与几何约束、材质、镜头和灯光。领域之间共享规则结构、参考索引、版本记录和评审证据，分别使用自己的样板与生产配方。
