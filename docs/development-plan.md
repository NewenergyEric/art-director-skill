# Art Director Skill 开发计划与验收目标

2026-10-09 · v0.1 · 游戏美术优先。开发验收已完成，结果见 [validation-report.md](validation-report.md)。

**目标：交付一套可分发、可独立调用、能把总监意图转成团队生产标准的 skill 工具包。** 母 skill 帮总监提炼和维护标准；生成的项目 skill 带着规则、视觉参考和版本进入成员的新会话，支持制作任务书、执行制作、逐条评审及规范变更。

目标模式已启动，当前开发范围包括方法、文件协议、可运行脚本、示例、测试与本地发布包。真实团队的长期美术效果试点属于采用验证，需要实际作品和总监参与；本轮不把虚构示例当成真实项目的风格验证。

**输入及取舍。** 合并了前轮 GitHub 调研和用户提供的 `art-director-skill-需求与方案.md`。附件中的流程是参考作者建议，用户已确定的游戏美术优先级继续有效。新核实的外部主张和依据见 [reference-reconciliation.md](reference-reconciliation.md)。

| 设计决定 | 实现方式 | 理由 |
|---|---|---|
| 保留母 skill 与项目风格包 | 母 skill 管建立/校准/打包/评审/演进；每个项目包是独立 skill | 实现总监到团队的交接 |
| 保留机器规则与人类说明 | `style-pack.json` 为唯一可编辑规范源；生成 `STYLE.md` 和项目 `SKILL.md` | 避免多个文件重复维护同一规则 |
| 规则有强度和证据 | must/should、理由、可变范围、参考 ID、检查方式与确认状态 | 固定边界，同时保留设计空间 |
| 参考图有明确分工 | style/identity/composition/material/context/counterexample/font | 减少跨参考污染 |
| 结构与艺术分别验收 | CLI 校验真实结构与文件；agent/人对视觉证据逐项评审 | 避免把解析成功或固定分数冒充美术通过 |
| 用发布快照交接 | 固定版本、内容指纹、文件校验清单、完整 ZIP；禁止原地改发布包 | 不依赖原聊天、绝对路径或自动更新 |
| 最小运行依赖 | Python 3.10+ 标准库；母 skill 在缺脚本环境时仍可指导工作 | 方便迁移到其他 agent 环境 |
| 自定义首版 token | 当前只保存简易颜色和字体字段，不声明 DTCG 兼容 | 不误称完整标准，也不为首版增加无关构建链 |

**本轮可验收目标如下。** 完成情况应以代码、命令输出和行为报告为证据。

| 编号 | 目标 | 验收证据 |
|---|---|---|
| G1 | 总监能从参考、已有规范、模糊意图开始，也能直接进入审片或变更 | 入口路由与按需参考；不强制每次重新探索 |
| G2 | 人物、场景、道具、字体/UI 均有可执行规则框架 | 游戏美术指南、四类 profiles、样例与八项试点任务 |
| G3 | 生成的项目 skill 可在另一个目录独立使用 | build 后重定位，verify 与 brief 成功，不引用开发机路径 |
| G4 | draft 可讨论但不能假冒获批版本 | release 校验拒绝缺少确认、参考或审批证据的包；示例保持 draft |
| G5 | 任务只加载适用规则，同时保留全局约束与角色身份 | 分类和 entity 的 brief 测试；无关类别不混入 |
| G6 | 参考、版本和改动可追踪 | 内容指纹覆盖引用文件；修改、删除、新增文件可被发现；diff 报告差异 |
| G7 | 没看图、没调用工具、缺少数据时准确报告 | 独立 agent 情境验证，明确 not_evaluated 与待定项 |
| G8 | 数据不被误当成命令，文件操作不越界或覆盖现有交付 | 相对路径/链接边界与拒绝覆盖测试；参考中出现指令不覆盖真实任务 |
| G9 | 可供总监和团队直接上手 | README、模板、虚构草案例子、八项试点卡、母 skill ZIP 和项目包 ZIP |

**开发分工与里程碑。**

1. **参考审计与协议确定。** 核实新方案的核心依据；确定 schema、状态与版本语义。交付本计划、审计记录与真实 JSON 模板。
2. **并行实现。** 工作流 agent 编写母 skill 和参考指南；工程 agent 编写可移植 CLI；独立测试 agent 编写黑盒验证；主 agent 整合协议、示例、使用文档和打包。
3. **整合和行为验证。** 运行结构验证与单元测试，修复已发现的问题；让新的 agent 在最少上下文下使用 skill，观察真实行为而非仅检查文档措辞。
4. **本地发布。** 生成可复制的母 skill ZIP、项目草案包和验证报告；准确标记哪些测试完成、哪些真实美术效果未实测。

**协议范围。** 核心字段包括项目与版本、显示上下文、设计意图、规则、参考索引、资产类别配置、角色身份、工具配方、决定、未定项与审批记录。数据类型与字段说明见 [style-pack-schema.md](style-pack-schema.md)。工作记录使用独立模板，避免成员输出污染规范包。

**首版交互体验。** 总监可以说“从这些参考提炼项目风格”“把这条返工意见变成明确规则”“按当前规范审这批资产”。成员可以说“按项目规范给主角做一个新姿势”“生成三件同系列道具”“这条需求与规范冲突，做一个例外提案”。skill 先识别模式与已有依据，只追问对当前任务确实重要的缺口。

**首版明确不承诺的能力。** 不训练模型或 LoRA；不硬编码未经校准的 0.92/0.95 相似度门槛；不靠提示词认证审批人；不从渲染图判断真实拓扑或引擎性能；不自动改所有成员的工具配置。外部生成工具按实际安装能力调用，工具缺失时交付可执行任务书。

**验证分三层。** 第一层用确定性测试检查数据、路径、哈希、构建、任务筛选和分发；第二层用独立 agent 验证沟通、证据边界与规范执行；第三层由真实总监开展多人试点，记录首次通过率、返工轮次、评审时间和身份漂移。前两层是本轮开发验收，第三层为上线后的效果验证，不混称为已经完成。

本轮完成后，推荐用一个真实游戏项目替换演示包的假设和空缺参考，再开展 `evals/pilot-tasks.json` 中的八项对照任务。依据试点结果决定是否加入引擎检查、DTCG 子集导出或额外模型工作流。
